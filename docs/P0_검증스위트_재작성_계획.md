## 1. 실패 2건의 진단

### 증상

```
환생메타_여유가_300회차_내내_1이상
  회차 201에서 여유 0.340        (기대 >= 1.0)

설계곡선이_실제_도달웨이브와_크게_어긋나지_않는다
  헤비: 실제 185 vs 설계 205 (90.2%)   (기대 > 95%)
```

### 원인 — 하나입니다

두 테스트 모두 **DPS를 단일 트랙으로 계산합니다.**

```csharp
int lv  = EconomyCore.AffordableLevel(cfg, purse);
var dps = EconomyCore.BaseDpsAtLevel(cfg, lv) * atkMul;   // 선형 트랙 1개
```

마스터문서 5.4가 명시합니다 — **"단일 트랙은 웨이브 70이 한계. 선형 4~5개를 곱해야 웨이브 200~300을 버틴다."**
그런데 두 테스트 어디에도 `UpgradeTracks`가 등장하지 않습니다. 오방색 곱연산이 빠진 모델로 회차 201의 여유를 재면 0.34가 나오는 것이 당연합니다.

두 번째 테스트는 여기에 하나가 더 겹칩니다. 비교 기준인
`TargetWave(k) = 37.7 × (k+1)^0.269`는 **승천이 웨이브 단독 조건이던 시절에 맞춘 곡선**입니다.
코어 게이트가 추가되어 티어가 늦게 오르는데 기준선은 그대로이니, 실제가 설계를 못 따라가는 것이 정상입니다.

부수적으로 `Simulate()`는 코어 일일 감쇠(`CoreGainWithDecay`)도 쓰지 않고 `CoreGain`을 그대로 씁니다.

### 결론 — 그리고 결론이 아닌 것

**결론:** 측정기가 고장 나 있습니다. README 미완 1번이 서술한 그대로입니다.

**결론이 아닌 것:** 경제가 멀쩡하다는 증명은 어디에도 없습니다.
지금 스위트로는 "깨졌다"도 "멀쩡하다"도 말할 수 없습니다. **그것이 이 작업이 1순위인 이유입니다.**

> 참고 — 헤비 페르소나의 실제 도달 185는 90일 목표 170을 이미 넘깁니다.
> 단일 트랙 모델로도 목표를 넘었으니, 5트랙을 넣으면 오히려 반대쪽
> (`ratio < 1.35`, 설계보다 너무 앞섬)이 걸릴 가능성이 있습니다.

## 2. 진실의 근원을 먼저 정합니다

작업 중 발견한 것입니다. **`CLAUDE.md`의 서술과 실제 위계가 다릅니다.**

`CLAUDE.md`는 "모든 수치는 스프레드시트가 유일한 기준"이라고 합니다. 그런데 스프레드시트 `가정` 시트 60~62행이 스스로 이렇게 적어두었습니다.

> ※ 스프레드시트 한계 — 승천 보너스를 도달 회차에 즉시 적용하고 있습니다.
> 실제로는 승천 후 다음 회차부터 적용되므로, 이 시트의 여유는 약간 낙관적입니다.
> **정확한 값은 C# EconomyCore 단위 테스트를 기준으로 하세요.**

같은 시트 42행에는 이런 메모도 있습니다 — *"티어 2 개방 50. C# 검증 결과 60→50 수정. 60이면 3~5회차 여유가 0.91로 진행 불가"*.

즉 **이미 C#이 스프레드시트를 고친 전례가 있습니다.** 실제 위계는 이렇습니다.

```
C# 검증 스위트  >  스프레드시트  >  마스터문서
```

**제안** — 재작성이 끝나면 `CLAUDE.md`의 해당 문장을 이 위계로 고칩니다.
지금 "유일한 기준"이라고 적혀 있는 탓에, 젬 12 vs 25 같은 충돌이 문서에 남아도 아무도 잡지 못했습니다.

## 3. 재작성 설계

### 3.1 시뮬레이터를 `BattleRunner` 기반으로

현재 `Simulate()`는 전투 루프를 **두 번째로 구현**하고 있습니다. 게임이 쓰는 경로(`BattleRunner.Tick`)와 검증이 쓰는 경로(`EconomyCore` 근사식)가 갈라져 있으면, 둘이 어긋나도 아무도 모릅니다.

→ 실제 `BattleRunner`를 구동하고, 업그레이드 구매는 `UpgradeTracks.BuyBest()`로 합니다. 게임이 하는 그대로입니다.

**단, 성능 문제를 먼저 확인해야 합니다.** 90일 × 3~6런 × 200웨이브를 `Tick(dt)`로 돌리면 EditMode 테스트가 몇 분으로 늘어날 수 있습니다. 테스트가 느려지면 안 돌리게 되고, 안 돌리는 검증은 없는 것과 같습니다.

- 목표: 전체 스위트 **30초 이내**
- 착수 첫 단계로 `dt`를 0.1 / 0.5 / 1.0초로 바꿔가며 도달 웨이브 편차를 측정
- 편차가 1웨이브 미만인 최대 `dt`를 채택. 그래도 느리면 `sim`만 Category로 분리해 수동/CI 실행

### 3.2 오방색 5트랙 도입 — 가장 큰 수정

`AffordableLevel` + `BaseDpsAtLevel`(단일 선형)을 `UpgradeTracks.BuyBest()`(5트랙 곱연산)로 교체합니다. 실패 2건의 직접 원인이 여기입니다.

### 3.3 `TargetWave()` 설계 곡선은 **지금 건드리지 않습니다**

`waveCoefficient(37.7)`과 `waveExponent(0.269)`는 스프레드시트가 **위험 파라미터**로 분류한 값입니다. 스트레스 테스트에서 지수를 0.40으로 올리면 여유가 0.00으로 붕괴한다고 기록돼 있습니다.

`CLAUDE.md`도 "수치를 임의로 바꾸지 말라"고 못 박고 있습니다.

**순서를 이렇게 잡습니다.**

1. 먼저 5트랙 + `BattleRunner`로 **실제 도달 웨이브를 측정만** 한다
2. 측정값과 설계 곡선의 괴리를 회차별로 표로 뽑는다
3. 그 표를 보고 재적합 여부를 **사장님이 판단**한다

측정 없이 계수를 만지면, 지금 깨진 측정기로 새 눈금을 그리는 셈이 됩니다.

### 3.4 4종 스위트의 역할 재정의

README는 `econ`/`cross`/`stress`/`sim` 4종이라 부르는데 실제 파일은 3개이고 이름도 다릅니다. 이렇게 정리할 것을 제안합니다.

| 스위트 | 역할 | 속도 |
|---|---|---|
| **econ** | 단일 함수 단위 — BigNumber, 비용·보상 곡선, 오프라인 공식. 스프레드시트 값과 직접 대조 | 빠름 |
| **cross** | **계층 간 정합성** — `EconomyCore` / `BattleRunner` / `UpgradeTracks`가 같은 입력에 같은 답을 내는가 | 중간 |
| **stress** | 파라미터 섭동 — 마스터문서 5.6 표(체력 1.09→1.12 등)에서 "진행 불가"를 실제로 감지하는가 | 중간 |
| **sim** | 페르소나 90일 커브, `BattleRunner` 실측 기반 | 느림 |

**`cross`가 지금 없는 계층이고, 이번 사고를 막았을 장치입니다.** 근사식과 실측이 갈라지는 순간을 잡아냅니다.

## 4. 광고 빌드 가드 (병렬, 30분)

### 현재 상태 — 이대로 빌드하면 사고입니다

```csharp
// GameController.cs:132  — 조건 없음
adService.Initialize(new EditorFakeAdProvider());
```

`EditorFakeAdProvider.Show()`는 **광고를 띄우지 않고 즉시 `onRewarded()`를 호출**합니다. 지금 APK를 만들면 광고 없이 모든 보상이 나갑니다.

### 제안 — 컴파일 단계에서 막되, 탈출구를 둡니다

```csharp
#if UNITY_EDITOR
        adService.Initialize(new EditorFakeAdProvider());
#elif ALLOW_FAKE_ADS_IN_BUILD
        adService.Initialize(new EditorFakeAdProvider());
        Debug.LogError("[AD] 더미 광고 프로바이더로 빌드됨. 스토어 제출 금지.");
#else
#error 광고 프로바이더가 주입되지 않았습니다. AppLovinAdProvider로 교체하거나,
#error 내부 테스트 빌드라면 Scripting Define Symbols에 ALLOW_FAKE_ADS_IN_BUILD를 추가하세요.
#endif
```

`EditorFakeAdProvider` 클래스 자체도 `#if UNITY_EDITOR || ALLOW_FAKE_ADS_IN_BUILD`로 감쌉니다.

**탈출구를 두는 이유** — 미완 목록에 없던 항목 중 하나가 *"앱 완전 종료 후 오프라인 누적 실기 검증"*입니다. 이건 **광고 SDK보다 먼저** 실기 빌드가 필요합니다. `#error`만 걸면 그 테스트를 못 합니다.

심볼을 일부러 추가해야만 빌드되고, 추가해도 실행 즉시 빨간 로그가 남습니다. "실수로 더미인 채 출시"는 구조적으로 불가능해집니다.
