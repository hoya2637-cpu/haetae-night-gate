**가설이 맞았습니다.**

- **도달 웨이브는 dt와 완전히 무관합니다.** 7개 구간 전부 77. 벽 판정이

- **런 시간만 dt에 비례해 부풀어 오릅니다.** `Tick` 1회당 웨이브를 최대 1개만

- **전체 62개 테스트가 0.38초에 끝납니다.** 성능 문제가 아예 없습니다.

## 2. 트랙 정책 비교

```
정책          | 도달웨이브 | 런시간(분) | 총레벨 | 전투배수
5트랙 BuyBest |         77 |      14.23 |     63 |      8.2
청 트랙만     |         73 |      13.28 |     56 |      6.6
차이          |          4 웨이브
```

### 이 측정은 대조군을 잘못 잡았습니다 — 정정합니다

제가 진단서에서 *"실패 2건의 직접 원인은 5트랙 곱연산 누락"*이라고 썼는데,
이 표만 보면 트랙 정책 차이는 **4웨이브**에 불과합니다. 제 서술보다 작습니다.

원인은 대조군입니다. "청 트랙만"도 여전히 `CombatMultiplier`(6.6배)를 적용받습니다.
반면 기존 실패 테스트가 쓰던 모델은 이랬습니다.

```csharp
var dps = EconomyCore.BaseDpsAtLevel(cfg, lv) * atkMul;   // CombatMultiplier 없음 = 1.0
```

**곱연산 항이 통째로 빠져 있습니다.** 8.2배가 아니라 1.0배입니다.
즉 진짜 격차는 "5트랙 vs 1트랙"이 아니라 **"곱연산 있음 vs 없음"**입니다.

→ 다음 계측에서 `CombatMultiplier = 1.0` 고정 대조군을 추가해 정확한 격차를 재겠습니다.


### 3.1 웨이브는 1.6~1.8배 앞서고, 티어는 설계대로 갑니다

**비율이 60회차 내내 1.56~1.81 밴드에 갇혀 있습니다.** 발산하지 않고 일정합니다.
즉 곡선의 *모양*은 맞고 *계수*만 낮습니다.

그런데 티어 진행은 다릅니다.

| | 회차 60 |
|---|---|
| 실측 | 티어 4 |
| 90일 커브 (3런/일 → 20일차) | 티어 4 |

**일치합니다.** 웨이브가 앞서는데 티어는 안 앞서는 이유는 **코어 게이트가 실질
병목**이기 때문입니다. 승천 이중 조건이 설계 의도대로 작동하고 있다는 증거입니다.
웨이브 단독 조건이었다면 티어가 연쇄로 뚫렸을 겁니다.

회차 40에서 실제 웨이브가 170 → 159로 **떨어지는 것도 정상**입니다.
티어 4 승천 시 코어 85%가 소각되기 때문입니다.

### 3.2 기존 테스트가 어느 쪽으로 틀렸는지 확정됩니다

격리해둔 `설계곡선이_실제_도달웨이브와_크게_어긋나지_않는다`는 이렇게 단언합니다.

```csharp
Assert.Greater(ratio, 0.95, "설계 곡선만큼도 못 갑니다 — 유저가 벽에 갇힙니다");
Assert.Less(ratio, 1.35, "설계 곡선이 현실과 너무 어긋나 환생 메타 검증이 무의미해집니다");
```

실측 비율은 **1.64**입니다. 실제로 걸리는 것은 하한(0.95)이 아니라 **상한(1.35)**입니다.
기존 테스트는 방향을 반대로 보고 있었습니다. "유저가 벽에 갇힌다"가 아니라
"설계 곡선이 현실과 어긋난다" 쪽이 맞습니다.

### 3.3 `TargetWave()`는 테스트 전용입니다 — 재적합의 성격이 바뀝니다

전수 조사 결과입니다.

```
EconomyCore.cs:105   TargetWave() 정의
Tests/*.cs           호출 6곳 (전부 테스트)
런타임 호출          0곳
```

`waveCoefficient(37.7)` · `waveExponent(0.269)`도 `TargetWave()` 외에는 쓰이지 않습니다.
**게임 플레이에 영향을 주는 값이 아닙니다.** 코어 획득량은 `TargetWave`가 아니라
`BattleRunner`가 실제로 도달한 웨이브로 계산됩니다.

따라서 계획서 3.3에서 제가 "위험 파라미터라 건드리지 말자"고 한 판단은
**절반만 맞았습니다.**

| | 성격 |
|---|---|
| **C# 코드에서** | 검증용 자 눈금. 고쳐도 게임은 안 변한다 |
| **스프레드시트에서** | 진행 모델 그 자체. 코어 획득·티어 통과가 여기서 파생된다 |

즉 스프레드시트의 `환생메타`·`90일커브` 시트 전체가 **실제보다 1.7배 낮게 잡힌
진행 모델** 위에 서 있습니다. 코드가 아니라 시트 쪽이 문제입니다.

## 4. 짚어야 할 것 — 런 시간이 10분을 넘습니다

```
회차 1   14.26분
회차 5   11.39분
회차 10  10.63분
회차 60   9.99분
```

- 마스터문서: **"런 1회는 처음부터 끝까지 10분 내외 유지"**
- `Unity_에디터_작업목록.md` 8장: **"첫 런은 11분"**
- 실측: 첫 런 **14.26분**, 10회차까지 10분 초과

포지셔닝의 핵심이 *"한 세션 5~10분, 후반에도 안 늘어남"*이라 그냥 넘기기 어렵습니다.

**다만 이 측정에는 오프라인 보상이 없습니다.** 매 런을 웨이브 1·코인 0에서
시작시켰습니다. 실제로는 직전 런의 최대 30%(광고 시 60%)를 받아 상당 구간을
건너뛰므로 런 시간이 짧아집니다. 문서의 *"2회차부터 6~7분"*이 그 효과입니다.

→ 오프라인을 넣은 조건으로 다시 재야 결론이 납니다. 다음 계측 항목입니다.

## 5. 판단이 필요한 것

### ① 설계 곡선을 어떻게 할 것인가

세 갈래입니다.

| 안 | 내용 | 장단 |
|---|---|---|
| **A** | 코드의 `waveCoefficient`를 실측에 맞게 재적합 (37.7 → 약 64) | 자 눈금이 현실과 맞아 검증이 의미를 되찾음. 단 스프레드시트와 코드가 갈라짐 |
| **B** | 코드는 두고 스프레드시트를 재적합 | 시트가 진행 모델의 근원이므로 근본 수정. 단 시트 전체 재계산이 필요하고 90일 커브·수익모델이 흔들림 |
| **C** | 둘 다 두고 검증 밴드만 넓힘 (`ratio` 상한 1.35 → 1.9) | 가장 싸다. 단 "왜 1.7배인가"를 영원히 안 보게 됨 |

**제 의견은 A + 시트 표기입니다.** 코드에서는 자 눈금이므로 재적합해도 게임이
안 변합니다. 시트는 지금 당장 건드리지 말고 "이 시트의 진행 모델은 실측보다
약 1.7배 낮다"는 주석만 남깁니다. 시트 재계산은 90일 커브·수익모델까지 파급되므로
별도 작업으로 떼어내는 것이 안전합니다.

다만 **B를 완전히 미루면 안 됩니다.** 소프트런치 코호트 분석에서 90일 커브를
기준선으로 쓰실 텐데, 그 기준선이 1.7배 어긋나 있으면 조기 소진 판단이 늦어집니다.
