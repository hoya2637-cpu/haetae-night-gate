## 2. 왜 한 회차만인가 — 자기 교정 구조가 있습니다

우연이 아닙니다. 구조적으로 그렇게 됩니다.

```
승천 → 전투력 하락 → 짧은 런 (도달 157)
                          ↓
              lastRunWave가 173 → 157로 떨어짐
                          ↓
        다음 오프라인 시작점도 156 → 140으로 내려감
                          ↓
                    헤드룸 22 회복
```

오프라인 시작 웨이브가 **직전 런의 결과**를 기준으로 산출되기 때문에,
한 번 짧은 런이 나오면 그 결과가 다음 시작점을 자동으로 낮춥니다.
**시스템이 한 런 만에 스스로 보정합니다.**

이것이 바로 처방을 서두르지 않은 이유입니다. 상한을 억지로 걸었다면
이미 존재하는 자기 교정을 덮어쓰는 셈이었습니다.

## 3. 이 문제는 티어가 올라가도 더 나빠지지 않습니다

승천 시 전투배수 비율을 식으로 풀면 이렇습니다.

```
비율 = (1 + 0.15c × 0.02) / (1 + c × 0.02) × 2.5        (c = 승천 전 코어)

c → ∞ 일 때  →  0.15 × 2.5 = 0.375
```

**최악이 −62.5%에서 포화합니다.** 실측이 이를 뒷받침합니다.

| 승천 | 실측 비율 |
|---|---|
| 1 → 2 | 1.14 (오히려 상승) |
| 2 → 3 | 0.57 |
| 3 → 4 | 0.42 |
| 이후 | → 0.375 수렴 |

티어 1→2는 코어가 적어 티어 배수 2.5가 소각을 압도합니다.
티어 5, 6, 7에서도 0.375보다 나빠지지 않으므로 **문제가 확대되지 않습니다.**

## 4. 그래도 신경 쓰이는 것 하나 — 광고 시청자가 더 나쁜 경험을 합니다

| | 승천 직후 런 |
|---|---|
| 광고 미시청 | 1.36분 |
| **광고 시청** | **0.73분 (44초)** |

광고를 본 유저가 시작 웨이브를 더 높이 받기 때문에, 승천 직후에는 오히려 손해입니다.
**수익에 기여하는 유저가 더 나쁜 순간을 겪는** 구조입니다.

다만 전체 평균으로 보면 광고 시청자가 유리합니다(5.94분 vs 8.18분 — 같은 진행을 더 빨리).
승천 직후 한 회차만 역전됩니다.

### 완화가 필요하다면 가장 싼 방법

`CalculateOffline`에 최소 헤드룸 K를 넣는 것입니다. 한 줄입니다.

```csharp
int powerCap = MaxClearableWave(c, coin, attackMultiplier) - minHeadroom;
```

`minHeadroom = 5` 정도면 44초 런이 약 2.5분이 됩니다.
**다만 지금 데이터로는 이걸 넣을 근거가 약합니다.** 자기 교정이 이미 작동하고 붕괴가 1회뿐입니다.

## 5. 제 권고

**다(그대로 둔다)를 채택하고, 대신 연출로 덮습니다.**

마스터문서 8.4에 이미 설계된 것이 있습니다.

> 각 티어 승천 시 정지 화면 한 장 + 한 줄. 스킵 가능.
> 티어 4 — *담장 안에서 웃음소리가 들린다*

**티어 진입 연출이 정확히 이 순간에 배치됩니다.** 짧은 런 앞에 티어 카피가 놓이면
"새 밤이 시작됐다"로 읽히지 "게임이 고장났다"로 읽히지 않습니다.
승천은 원래 리셋을 동반하는 이벤트이고, 그 대가가 한 런이라면 납득 가능한 범위입니다.

**단, 소프트런치에서 확인할 지표를 지금 정해둡니다.**

- 승천 직후 세션의 이탈률 vs 평시 세션 이탈률
- 승천 직후 광고 시청률이 떨어지는가 (44초 런을 겪은 유저가 다음 광고를 거부하는가)

이 둘 중 하나라도 유의하게 나쁘면 그때 `minHeadroom`을 넣습니다.
**계측 하네스가 이미 헤드룸을 추적하므로 판단 근거는 언제든 다시 뽑을 수 있습니다.**
